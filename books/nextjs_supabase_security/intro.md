Next.js と Supabase の組み合わせは手軽に本番まで持っていけますが、その手軽さの裏で「どこで守っているのか」が曖昧になりがちです。この本では、情報漏えいを防ぐために最低限押さえておきたい設計と運用を、よくある誤解から順に整理します。

## 想定読者

- Next.js（App Router）＋ Supabase で本番運用している、またはこれから運用する開発者
- RLS は書いたことがあるが、それで十分なのか不安な人
- toC と toB（マルチテナント）のどちらかで、権限設計を見直したい人

## この本でわかること

- Supabase の API がブラウザから直接呼べることの意味と、そこから導かれる設計方針
- RLS・GRANT・ビュー・`security definer` 関数の落とし穴と、コードでの対策
- secret key の安全な扱い方と、Server Action での認証・認可
- WAF/CDN やレート制限で「できること」と「できないこと」
- toC と toB で変わるリスクと対策、最初にやるべきチェックリスト

## 結論

**Supabase は publishable key でブラウザから直接 API を叩ける前提で設計し、DB 側（RLS・権限）を最後の砦にする。** その上で、Next.js 側の認証・認可、鍵の管理、ログと対応手順を重ねて多層で守ります。

なお、ここに書いたことをやれば絶対に安全、というものではありません。「最低限ここまではやっておきたい」という線引きとして読んでください。
