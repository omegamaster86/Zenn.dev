---
title: "toC と toB（マルチテナント）"
---

| 観点 | toC | toB（複数テナント） |
| --- | --- | --- |
| 主なリスク | 公開登録の悪用、bot による大量登録、不正ログイン（パスワードリスト攻撃）、スクレイピング | 企業間のデータ混在、権限の過剰付与、退職・異動者のアクセス残存、管理者アカウントの乗っ取り |
| データ分離 | 本人データの分離（`auth.uid()` 基準の RLS） | 企業（テナント）単位の RLS＋企業内の役割による制御 |
| 認証 | CAPTCHA、回数制限、MFA の任意提供 | SSO（SAML SSO は Pro 以上）、管理者 MFA の必須化 |
| 認可の根拠 | 本人 ID | 所属テーブル（membership）上の所属と役割 |
| 運用 | 不審登録・大量取得の監視 | 監査ログ、退職・異動時の権限解除、権限変更の通知 |

toB で特に注意する点：

- **リクエストに含まれる企業 ID を信じない**。サーバーと RLS の両方で、ユーザーが実際にその企業に所属し、必要な役割を持つかを所属テーブルで検証する（toB・Server Action 章参照）。
- **`user_metadata`（`raw_user_meta_data`）はユーザー自身が編集できるため認可に使わない**。認可情報は `app_metadata` か自前の所属テーブルで管理する。JWT のクレームはトークンが更新されるまで古い可能性がある点にも注意。
- 最終的には toC / toB というラベルではなく、**扱うデータの機密性と漏えい時の影響**で対策の強さを選ぶ。
