## アカウント乗っ取り

正規ユーザーのアカウントが盗まれると、RLS は**そのユーザーの権限内の読み出し**を止められません。

- MFA を提供し、特に管理者は必須化する。必須化はフロントだけでなく、RLS で `aal2` を要求するなどサーバー/DB 側で強制する（toB 章の MFA 参照）。
- 権限変更や大量取得を監査ログに残し、通知する。
- アカウント停止とセッション失効の対応手順を用意しておく。

## セッション失効の限界

**セッションを失効させても、発行済みのアクセストークン（JWT）は有効期限まで即座には無効になりません。** ユーザーを削除した場合も同様です。

- JWT の有効期限を適切に短くする。
- 厳密さが必要な重要操作では、JWT の `session_id` が `auth.sessions` に存在するかを確認する。
- セッションの最大寿命や非アクティブタイムアウトなどの機能は Pro 以上の提供（料金ページで確認）。

## 大量取得の抑止とデータ最小化

- 1回あたりの件数制限だけでは、ページングを繰り返す取得は止められない。**ユーザー／企業単位で一定期間の累積取得量**を制限・記録し、大量エクスポートは監視・通知の対象にする。
- 不要なデータは持たない、返さない（`select *` の結果をそのままクライアントに渡さない）。
- 機密情報（個人を特定できる情報、決済関連など）は別テーブル・別スキーマに分離し、アクセス経路を絞る（Server Action 章のサーバー集約参照）。
- 必要に応じて、DB とは分離した鍵管理による暗号化を検討する。ただし暗号化はアクセス制御の代わりにはならない。

## ログと検知

- Auth の監査ログ、API・DB のログで、ログイン失敗の連続、RLS や権限による拒否の増加、短時間の大量アクセス・大量取得の兆候を見る。
- ログから攻撃かどうかを自動で完全に判定することはできない。
- 自動アラートや自動対応が必要なら、外部の監視基盤との連携（例：Log Drains。Pro / Team / Enterprise などプラン条件あり）と、アラートの閾値・担当者・初動手順を自分たちで用意する。ログの保持期間もプランによって異なる。

## 開発・運用の衛生

- 依存パッケージ（Next.js、`@supabase/*` など）を継続的に更新し、セキュリティアドバイザリを追う。
- リポジトリと CI でシークレットスキャンを行い、秘密鍵の混入を検知する。
- RLS と権限の自動テストを CI に入れる（チェックリスト章のケース）。Supabase の Security Advisor の指摘も確認する。
- バックアップは破壊や障害からの**復旧**のための対策で、漏えいそのものは防がない。
