# エンジニア像に関してちょっと整理
大まかにまとめたAI前、AI後の典型像です。
このように見ると何もかもが変わっている気がします

| | AI前の典型像 | AI後の典型像 |
| --- | --- | --- |
| **仕事の中心** | 仕様やチケットを受け取り、自分の頭と手で設計→コーディング→テスト→PR。ジュニアは定型実装・バグ修正で土台を固める。「読める・書ける・デバッグできる」が評価の主軸 | たたき台の実装はAIに任せる場面が増え、人は何を作るか・採用するか・品質に責任を持つ側へシフト |
| **分業** | PM / デザイン / QA と分かれ、エンジニアは渡された要件をきれいに実装する立場が強い（受託・大規模）。上流は別職能、実装は下流 | 分業は残りつつ、顧客理解・課題設定・分解まで踏み込む必要性が増す |
| **学習** | 公式ドキュメント、Stack Overflow、先輩、書籍など。試行錯誤に時間がかかり、最初のたたき台は自分で書く前提 | 調査やたたき台の初速はAI。理解できているか・検証できるかが学習の芯 |
| **レビュー** | 人が書いた差分の理解・品質・設計確認が中心。出力量は手作業の速度に上限 | 人とAIの差分が増え、レビュー量も増える。バグ探しに加え、同期点と責任の確認が重要に |
| **キャリアの語り方** | 深める／広げる／別職能へは昔からあるが、「実装経験の年数」が説明しやすい材料だった | 年数に加え、定義・検証・責任・ドメイン・AIの使い方など、語れる材料が増える |

# 実装や生産性が上がったが？？
**開発が速くなるのは良い、しかし提供する価値をもっと高くする必要がある**と個人的には思っています。

顧客的には開発が早くなり、提供スピードが早くなるのは良いことです。結果的に納期の短縮、金額的な負担が減ります。
今までなら開発スピードに各社の差が出ていました。しかしCursor、Claude Code、Codex、Devinこの辺が登場してからは、各社の開発スピードに差は無くなってきました。
https://tech.acesinc.co.jp/entry/2026/03/19/083000
https://tech.sompo.io/entry/2025/06/20/082235
このようにほとんどの会社では開発にAIを使用するのは当たり前になってきています。
そして当然ながらほぼ全ての会社でAIを使用していれば、そこまで開発スピードに差はありません。では次に顧客に選ばれるにはどうしたらいいでしょうか？
個人的な答えではありますが、**顧客の業務を理解し、課題を解決できる力です（価値ともいう）。**
- なんでそれを作るか？
- どうやって実装するか？
- これを提供したことで顧客の課題は解決できるのか？

上記をしっかり見極めないといけません。そして顧客会議に参加し1次情報を取得する。
今まではPMが行ってきた内容だと思いますが実装をAIがやる以上、エンジニアが価値提供をするために考えないといけません。FDE的な動きがほぼ全てのエンジニアに求められています。

# 何を学ぶ？

前の節で書いた「顧客理解・課題解決」は、いきなり身につくものではないので、**何を学ぶか**を意識しておくのが大事だと思います。
新しいフレームワークを学ぶのももちろん良いですが、**AIが速くしても代替しにくい能力**に時間を割く方が優先な気がします。

### 顧客の業務と課題（ドメイン＋ヒアリング）

価値提供の土台は、コードより先に**顧客の世界を理解できているか**だと感じています。

- 業務フローをもとに知識を体系化する
- 現場の制度や文化
- 意思決定のロジック
- 顧客会議などで**1次情報**を取り、要望と本当の課題を切り分ける
- 「やりたい機能」ではなく「何が楽になる／何が減るか」を言語化する

AIが爆速なアウトプットを出すので、仕様や仮説の精度が重要です。爆速アウトプットができても、仮説がボロボロだと顧客の期待値と異なり、失望されてしまいます…
そうならないためにも仮説が必要であり、仮説を立てるにはドメイン知識や1次情報が必要になってきます。

顧客会議などで**1次情報**を取り、要望と本当の課題を切り分ける。これは1番難しいと思っています。下記は1例です。
https://note.com/shin_suge/n/n44cbf15b2151
> チームが本当に困っていたのは「日報を書く時間」ではなかったんです。 本当の課題は 「日報から学びを得る仕組みがない」 ことでした。

困りごととして顧客から聞く情報は表面上だけの可能性があります。本当の困りごとは結構省略されることがあります。営業として初回ヒヤリングを行うこともありますが、私自身、本当の困りごとをヒヤリングできている自信はあまりないです。

### 課題の分解と「作る／作らない」の判断

実装の初速はAIに任せられる一方、**何を作るか・採用するか**は人の仕事になります。

- 要件の分解（Must / Later、先に検証すべきリスク）
- コスト・納期・保守・セキュリティなどの**トレードオフ**を説明できること
- AIが出した案を、そのまま採用せず**却下する理由**を持てること

ここは設計の教科書だけでは足りず、**小さく出してフィードバックをもらう**経験の積み上げが効くと思います。

### AIを道具として使う力

開発スピードが平準化する前提では、**同じ土俵でAIを使いこなす**のは前提条件です。ただし差別化の主役というより、他の能力を支える基礎線だと捉えています。

- 仕様・制約・既存コード・失敗例など、**コンテキストを渡す**力
- 出力をそのままマージせず、**最後の責任は人が持つ**使い方
- うまくいかないときに、プロンプト・問題定義・技術選定のどこがずれているか見る

### 伝える・合意する

FDE的に動くなら、実装だけでなく**周りを巻き込む**学びも必要です。

- 非エンジニア向けに、効果・リスク・選択理由が伝わる説明
- スコープ・前提・やらないことの**合意形成**
- PM・デザイン・QAと役割をすり合わせる（全部一人でやる必要はないが、境界は理解したい）
